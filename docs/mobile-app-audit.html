01 High

Refresh tokens sit in plaintext SharedPreferences, and Android backs them up

Security

lib/core/sync/services/auth_service.dart:113 · android/app/src/main/AndroidManifest.xml

saveToken() writes the whole AuthToken — access and refresh token — as jsonEncoded text into SharedPreferences. flutter_secure_storage is not in pubspec.yaml, so nothing reaches Keychain or Keystore.

The manifest sets neither android:allowBackup nor dataExtractionRules, so it defaults to true. The backing XML — refresh token included — is swept into Android auto-backup and into adb backup. A refresh token is a long-lived credential: whoever holds it can mint access tokens until it is explicitly revoked server-side.

Fix Move the token pair to flutter_secure_storage, and set android:allowBackup="false" (or exclude the prefs file via dataExtractionRules). Migrate existing users by reading the old key once, re-writing it securely, then deleting it.

02 High

The local database is unencrypted, and it holds the most sensitive content in the app

Security

lib/core/database/sync_database.dart · pubspec.yaml

There is no SQLCipher dependency and no PRAGMA key anywhere in the database layer. Every note, prayer, prayer log, person record and Bible bookmark is stored as plaintext SQLite.

This app's data is unusually personal — private prayers, named people, spiritual journaling. It inherits the same allowBackup problem as the token above, so the entire corpus leaves the device in backups. This is a product-risk call as much as a technical one.

Fix At minimum, close the backup escape hatch alongside finding 01. If the threat model includes a lost or shared device, encrypt at rest with sqlcipher_flutter_libs and a Keystore-held key — plan it as a migration, since it rewrites the database file.

05 Medium

Reactive queries are almost entirely unbounded

Performance

lib/core/sync/repositories/ · 45 watch() vs 4 limit()

The repository layer exposes 45 .watch() streams and applies .limit() in only 4 places. Providers such as notesStreamProvider therefore hydrate the user's entire table into memory, and re-emit the whole list whenever any single row changes.

Every write — including one arriving from sync — re-runs the query, re-materialises the list, and rebuilds each screen watching it. Cost is proportional to total corpus size rather than to what is on screen.

Already changed. Two cheaper parts of this are done. The list-backing reads no longer decode each row's per-field merge timestamps — measured at 8.3ms per five autosaves over a thousand rows — and the note editor's autosave debounce went from 300ms to one second, which cuts the re-delivery rate during typing by more than three. A .distinct() filter was investigated and rejected: every write bumps both updatedAt and version, so consecutive emissions genuinely differ and the filter would never fire. autoDispose was rejected for the same kind of reason — StatefulShellRoute.indexedStack keeps every visited tab mounted, so the streams stay subscribed for the life of the process regardless.

Fix — what is left Page the list-backing streams (a limit tied to the scroll position), and for counts use a COUNT(*) watch instead of watching rows and calling .length. Neither of the changes above reduces the number of rows a query returns, which is what the 45-vs-4 ratio above is actually about.

06 Medium

Nineteen files exceed 800 lines, concentrated in screens that mix four concerns

Maintainability

19 files > 800 LOC · 44 files > 500 LOC

notes_home_screen.dart (1,881 lines) holds the folder tree, the notes list, smart collections, filtering, sorting, multi-select and the trash view across just two classes. group_detail_screen.dart (2,038) spreads its six tabs over twelve classes and twenty-seven private methods — roughly seventy-five lines apiece.

The consequence is the one already visible above: because everything shares one build(), unrelated state changes trigger the expensive tree and list work. Splitting the file is what makes finding 05 straightforward rather than delicate.

Fix Extract each section into its own ConsumerWidget so rebuilds scope naturally. Start with the two sections named in finding 05 — the refactor and the performance fix are the same edit.

07 Low

Nineteen files still carry hardcoded strings, and a sweep will not fit all of them

i18n

19 files with no l10n reference · 1,452 call sites against a 973-key catalogue

Every file that renders UI chrome and has a BuildContext has been swept. What is left divides three ways, and only one of them is a sweep.

Content, not chrome. daily_scripture_widget.dart holds seventeen verses and their references; bible_books.dart names the sixty-six books; suggested_prayers.dart is the local default for a remote-config key. A translator should not be translating scripture — a localised build swaps Bible translation and takes its prayer copy from the server.

Not user-facing. watch_bridge_service.dart, widget_data_publisher.dart and several models hold log lines and debug output.

The real remainder. auth_providers.dart builds fourteen English error strings — “Login failed”, “This email is already registered” — inside a provider with no context, and sets them straight into AsyncValue.error for a screen to render. UserFacingError does the same thing one layer up. Localising these means the provider raising a typed error and the screen choosing the copy, which is an error-handling change rather than a string sweep.

Fix Give the auth and load paths an error type per failure, and let the screen pick the wording. Leave the scripture, the book names and the remote-config defaults alone — they are data, and the sweep would make them worse.
